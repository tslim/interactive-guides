What this model includes—and deliberately leaves out

One output queue, one outgoing link, fixed travel time, and a burst already at the router. B packets have the same size as A packets and a predetermined interleaving. Real routers do not promise this scheduling pattern.

The loss switch drops A2 once in transit. The delay switch adds extra travel time to A1 to demonstrate reordering. Neither is a claim that internet packets normally take random paths.

The TCP-style model retries A2 after a toy timeout of 1,000 ms from the end of its initial transmission. The retry joins the same queue. Actual TCP uses acknowledgments, adaptive loss detection, flow control, and congestion control; these are not simulated. ACK traffic, connection setup, other hops, and link-layer overhead are omitted.

Both models use the same illustrative 40-byte header allowance so the comparison isolates delivery behavior. Real TCP and UDP overhead differs. Event playback advances one event per beat, not in real-time proportion to the modeled clock.

1 · A message becomes pieces

Smaller pieces can share the link—but need more headers.

A packet carries payload plus information used to deliver it. Splitting a transfer lets packets from different senders take turns instead of reserving the whole path for one message.

Is a message the same as a packet?

No. An application defines messages. TCP carries a byte stream and divides bytes into segments; IP carries packets; link technologies carry frames. Each layer has its own information and boundaries.

A TCP write does not necessarily become one segment or one read at the receiver. Applications need their own way to mark message boundaries. UDP preserves datagram boundaries, but a UDP datagram is still carried inside IP.

The A1/A2 labels in this guide identify successive groups of data, not real TCP message numbers. Packet sizes are also constrained by maximum transmission units (MTUs); arbitrarily large packets are not a free optimization.

2 · A network of networks

Routers choose the next hop, not a private wire.

The routing picture is separate from the single-link experiment. Real route changes take time and can temporarily lose packets. A flow often keeps a stable path; alternate paths are possible, not mandatory for every packet.

How is this different from circuit switching?

A circuit-switched system reserves resources along a path for a conversation. Packet switching lets many conversations share link capacity as packets arrive. That flexibility also means waiting and congestion when demand exceeds available capacity.

The internet is not one central router. Network operators exchange routing information, and routers forward packets using the information available to them. A chosen route need not be the geographically shortest one.

3 · Bandwidth, latency & congestion

More capacity does not make the signal travel faster.

Capacity is how many bits a link can transmit per second. Propagation delay is how long a signal takes to travel. Queueing delay is waiting for an occupied link.

A faster download and a more responsive conversation are not the same thing.

What changes when the network is busy?

Packets wait behind other packets at an outgoing link. More waiting increases latency without changing the link’s propagation time. If a finite buffer fills, packets can be dropped. Your application’s throughput can be below the link’s capacity.

Try “Shared link” or “Busy link + loss” above. Competing packets extend the queue; the explicit loss switch is a separate controlled failure, not a simulated buffer-overflow algorithm.

Latency is a broad term. Round-trip time (RTT) includes the trip out and back, plus other delays. The travel-time slider here describes only one-way propagation on the modeled link.

4 · Loss & ordering

Arrival order is not always delivery order.

TCP: an ordered byte stream

The receiver can buffer later bytes while an earlier gap remains. The sender detects loss and retransmits. The application receives bytes in order.

The cost can be waiting: later data in that stream cannot skip missing earlier bytes. Persistent failures can still terminate the connection.

UDP: individual datagrams

UDP itself does not recover missing datagrams or order them. The application receives what arrives and decides what to do next.

That does not force applications to ignore losses. They can add sequence information, recovery, congestion control, and other behavior.

What about QUIC and HTTP/3?

QUIC runs over UDP but adds secure connections, loss recovery, congestion control, and reliable ordered streams. “Uses UDP” does not mean “the application accepts unreliable delivery.”

Ordering is per QUIC stream. Missing data on one stream need not block delivery on another, although the streams still share network resources. HTTP/3 uses QUIC; it does not eliminate latency or congestion.

Does a TCP acknowledgment mean a message was read?

No. Transport acknowledgment means the receiving transport has acknowledged bytes. It does not prove the application processed them, saved a file, or showed a chat message to a person. Applications need their own receipts for those meanings.

Why not just use UDP for every live application?

A real media application still needs to handle variable delay, loss, network congestion, and security. Jitter buffers delay playback slightly to absorb timing variation. Missing audio may be concealed, recovered, or skipped depending on the deadline.

A download normally needs every byte. A chat application usually needs complete messages, prompt delivery, and application-level receipts. A live call also cares whether data arrives while it is still useful. Protocol choice depends on all of these needs.

The payoff · Chat without refreshing

Who gets to speak next?

Packet switching moves data. Web messaging patterns decide when the application sends it. Compare repeated questions with a channel that stays open.

One-way events: SSE

The browser opens an HTTP event stream. The server sends updates through it. A browser action can use a separate HTTP POST—it need not create a separate physical connection.

Two-way messages: WebSocket

After an opening handshake, either endpoint can send framed messages. A WebSocket message is not necessarily one network packet. A secure wss:// connection also protects traffic with TLS.

WebSockets remove the need to keep asking for updates. They do not remove network delay.

Does WebSocket bypass TCP’s ordering delays?

No. The classic WebSocket protocol runs over TCP. Missing earlier bytes can delay later WebSocket messages on that connection. WebSocket supplies message framing; TCP supplies the ordered byte stream underneath.

Polling does not necessarily establish a new TCP/TLS connection every time. SSE and WebSocket need connection management and recovery too. Reconnection alone does not guarantee that every missed message is replayed.

These are common patterns, not a complete catalog. Long polling, where the server holds a request until an update or timeout, is another option.

Keep the layers separate.

Packets share links. Routers choose next hops. Transport protocols shape delivery. Applications decide what data is useful—and when to send more.
