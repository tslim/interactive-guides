Packets, segments, frames, and messages?

Applications define messages. TCP carries a byte stream in segments; IP carries packets; links carry frames. A TCP write need not equal a segment or a read. Applications must mark message boundaries. UDP preserves datagram boundaries.

A1/A2 label data groups, not TCP message numbers. Real maximum transmission units (MTUs) limit packet sizes. Both delivery models here use an illustrative 40-byte header, not exact real-world overhead.

Where does this link fit in the internet?

Routers forward packets from one network to the next using next-hop information. This journey zooms into just one of those outgoing links.

The primary route is selected. This separate topology illustration does not change the transfer’s timings.

Paths often remain stable for a flow. Route changes take time and may lose packets. Routers select next hops, not necessarily the geographically shortest path. Packet switching shares capacity; circuit switching reserves resources.

3 · Cross the link

Transmit bits. Then travel.

Putting all a packet’s bits onto the link takes time. After its last bit leaves, another packet can transmit while the first keeps travelling.

Why do file downloads and tiny replies feel different?

Tiny reply (240 B): 20 ms transmission + 60 ms travel = 80 ms.

Small file (240,000 B): 20,000 ms transmission + 60 ms travel = 20,060 ms.

These ideal one-hop estimates use the current capacity and travel time but omit headers, queueing, setup, and other hops. They are not this transfer’s measured duration. Increasing capacity helps the large file more; reducing travel time helps both.

The slider is one-way propagation, not round-trip time. Real application throughput can be below link capacity. Busy buffers can drop packets; our loss toggle is a controlled failure, not simulated buffer overflow.

TCP adds recovery and ordering. Bare UDP leaves those decisions to the application.

What is simplified about recovery here?

A2 is lost once. The TCP-style retry joins the router queue 1,000 ms after A2’s first transmission ends. Real TCP uses acknowledgments, adaptive loss detection, flow control, and congestion control. Setup and ACK traffic are omitted here. Persistent failure can still end a TCP connection.

Delaying A1 is a controlled out-of-order case, not a claim that every packet takes a random route. The event inspector shows actual arrival and release times for the same run.

Does UDP mean unreliable apps—or always faster?

No. Applications can add recovery, ordering, security, and congestion control. QUIC runs over UDP and adds these capabilities with separate ordered streams. HTTP/3 uses QUIC; loss on one stream need not block another. Network delay still applies.

What do these audio deadlines represent?

All numbered chunks are ready initially. Chunk 1 is due at 300 ms, then one every 150 ms. Deadlines are invented and anchored to this burst—not a full live call. Changing packet size changes the toy chunk boundaries and count, not a realistic audio encoding.

Data must be released to the app by its deadline, not merely arrive at the receiver. Real media also needs security, congestion handling, and jitter buffers. Missing audio may be concealed, recovered, or skipped.

Does delivery prove an app saved or read the data?

No. A TCP acknowledgment confirms transport receipt—not processing, saving, or human reading. Chat needs complete messages plus application-level receipts. Applications must also arrange datagrams into the right order when using bare UDP.
