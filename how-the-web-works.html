1 · The address

Read the address.

A URL identifies a resource—not the page itself.

Model notes

“Server” describes a role: software that responds to requests. It can run on one computer or a large fleet. The browser is the client. The same computer can play both roles in different conversations.

A URL can also contain a query such as ?sort=name and a fragment such as #care. The query is sent in the request; the fragment is handled by the browser and is not sent in the HTTP request.

2 · Domain Name System

Turn a name into an address.

DNS links names like garden.example to the IP addresses connections use.

Model notes

The checkbox changes only this DNS illustration. “Repeat visit” in Journey combines DNS caching with cached page resources.

A recursive resolver does lookups for its clients. An authoritative nameserver publishes records for a DNS zone. A resolver can ask several servers to find an answer; cached referrals often shorten this process.

A record’s TTL limits how long that cached answer is normally reusable. Changing a DNS record does not instantly replace every cached copy. One name can also return several addresses, or point to another name.

The example domain is reserved for documentation. The referral sequence here explains the real mechanism; it is not a live lookup of .example.

Model notes

Destination IP addresses, timing, and traffic sizes can remain visible. DNS or connection setup may expose the hostname.

A valid certificate does not prove content is true or software is bug-free. Try “Invalid certificate” in Journey: this model stops before sending HTTP.

HTTP/1.1 and HTTP/2 normally use TCP. HTTPS adds TLS. HTTP/3 uses QUIC over UDP, with TLS security integrated into QUIC; it does not use the TCP handshake shown here.

Browsers can reuse existing connections and resume secure sessions. Not every click repeats every setup step. Our repeat-visit preset deliberately uses a new connection so you can isolate the effects of caching.

200 The request succeeded.

404 This resource was not found.

500 The server encountered an error.

404 and 500 are HTTP responses. DNS failure means HTTP never started.

Model notes

Change “Requested path” in Journey to compare responses. HTTP/2 encodes messages in binary frames. Some requests, such as a form submission using POST, also carry a body.

A redirect response, such as 301 or 302 with a Location header, can send the browser to another URL. The browser then makes another request.

HTTP is not only for HTML. An API might return JSON; an image request returns image data. The Content-Type header describes the response body’s format.

5 & 6 · Resources & rendering

Turn resources into pixels.

One page often means many requests.

Model notes

The preview is a controlled illustration, not another webpage load. Images carry separate data; scripts can handle events and change the document.

The browser need not wait for everything: it can discover resources while parsing HTML, fetch several concurrently, and show content early. Some stylesheets and scripts can delay rendering or parsing. Our stepper separates these activities so you can see their roles.

Not all interactivity needs JavaScript: links, native form submission, and expandable details elements can work without it. JavaScript powers the custom watering action in this example.

Why is a repeat visit sometimes faster—or out of date?

A browser may reuse fresh cached CSS, images, and scripts instead of downloading them again. A stale response can sometimes be validated with the server; a 304 Not Modified response lets the browser reuse its cached body.

Our repeat-visit preset assumes a usable DNS answer and fresh cached assets, but fetches the HTML again over a new connection. Real cache behavior depends on headers and browser state. Cache-Control: no-cache means validate before reuse, not “never store.”

One more request · Cookies & authentication

Remember a sign-in.

Model notes

This toy login assumes credentials passed. It never requests a password, sets a real cookie, or persists state; reloading clears the demo. Cookies can also store preferences, not just session IDs.

Being signed in does not grant access to other users’ files or administrator controls. The server must check permissions separately.

What do Secure, HttpOnly, and SameSite mean?

Secure restricts the cookie to secure transport in normal use. HttpOnly prevents page JavaScript from reading it through document.cookie; the browser can still send it with requests.

SameSite controls sending in cross-site contexts and helps limit some cross-site request forgery (CSRF) attacks. It is not a complete security solution. Domain and path rules also affect which requests receive a cookie.

The response uses Set-Cookie to store a cookie. Later requests use Cookie to send matching name/value pairs. The cookie’s attributes are not repeated in that request header.

Are cookies the only way to authenticate?

No. Applications can use other credentials, including bearer tokens in an Authorization header. Passkeys, passwords, and identity providers are different ways to establish identity. This guide illustrates only one common server-side session design.

A real sign-in system also needs safe credential handling, session rotation, expiry, server-side permission checks, and defenses against attacks. This demo is not a login implementation to copy into a product.

Keep the model.

Name → address → connection → HTTP → pixels. Sessions connect later requests.
