How the patterns work & model notes

Polling asks every five seconds. Updates wait for the next request.

Polling asks for news; SSE pushes server events, with browser replies using separate HTTP requests; WebSocket lets both sides send on one channel. Messages are not individual packets.

The shop creates news at 1 s. Polling receives it at 5 s: four seconds of application waiting. SSE and WebSocket receive it at 1 s in this model because transit and processing are omitted. Switching patterns preserves the same moment.

Playback advances one meaningful event per beat, skipping quiet seconds. The same checkpoints are used for every pattern: messages at 1, 2, 6, and 7 s, plus polling times at 5 and 10 s. Polling times remain visible when comparing an open channel. Tokens show direction, not speed. Transit and processing are omitted to isolate app waiting.

Classic WebSocket uses TCP: missing earlier bytes can delay later messages. WebSocket adds framing; wss:// adds TLS protection.

A separate HTTP request need not create a new physical connection. All patterns need connection management; reconnecting does not guarantee replay. Long polling—holding a request until news or timeout—is another option.
