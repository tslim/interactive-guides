4 · Execute in parallel

CPU cores favor flexible, low-latency work; GPUs favor throughput across many grouped lanes. Compare both buffers as their illustrative waves finish.

CPUs combine sophisticated cores, vector instructions, and multiple threads. GPUs organize many execution lanes into groups for suitable parallel work. The two CPU and eight GPU lanes shown here are teaching choices, not physical core counts. Lanes cooperate on tiles and instructions; there is not one GPU core per neuron.

Model assumptions & what this leaves out

This local model uses a 1- or 8-row input with four features and a 4 × 4 weight matrix. The optional conditional adds 1 to nonnegative dot products or subtracts 1 from negative ones. It is not ReLU or an implementation recommendation.

The comparison aligns narrative steps within each stage, not physical time. Two illustrative CPU output lanes and eight GPU lanes in groups of four process the same work. If one path has fewer steps, its snapshot and charged work stay fixed while the other continues. This does not introduce a real cross-device synchronization barrier or suggest both alternatives are executed together.

Real CPUs use caches, SIMD, out-of-order execution, and multiple threads. GPUs have compute units, registers, caches, grouped execution, and sometimes specialized matrix hardware. The drawn lanes, wave sizes, and synthetic cost units are not hardware specifications or performance measurements.

Preparation, transfers, submission, arithmetic, and completion have chosen integer costs. Resident weights describe an earlier request’s state. Hardware access is assumed configured; the OS/container/VM explanation does not gate the main journey.

This is one discrete-GPU workflow whose caller needs output in system memory. Integrated GPUs, unified memory, direct device consumers, transfer overlap, streams, and coherent architectures can change or avoid these copies and waits. Synchronization is not universally a host copy.
